# BM Industrial Solutions website

Static site for [BM Industrial Solutions](https://www.bmindustrialsolutionsllc.com/),
built with [Astro](https://astro.build). Every page is prerendered to plain HTML
in `dist/`; no JavaScript framework ships to visitors.

## Layout

```
src/
  data/content.ts          All copy and data: services, areas, nav, company
  data/reviews.json        Google reviews, generated by _build/reviews.py
  pages/                   One file per route
    index.astro              Home
    about/ contact/          About, Contact + quote form
    services/index.astro     Services hub
    services/[slug].astro    All 9 service pages, one per SERVICES entry
    service-areas/index.astro      Service areas hub
    service-areas/[slug].astro     6 city pages, one per AREAS entry
    404.astro  sitemap.xml.ts  robots.txt.ts
  components/              Reusable pieces: nav, cards, bento, FAQ, photo...
  components/sections/     Blocks shared across pages (reviews, emergency band)
  layouts/Base.astro       Page shell: head, metadata, nav, footer
  lib/                     URL helpers and structured data
public/assets/             css, js, images (copied to dist/ as-is)
brand/                     Logo kit masters (SVG) and colours; see "Logo" below
_build/                    check.py, pages.sh, and the photo/review importers
```

Routes:

```
/                          Home
/about/  /contact/
/services/                 Services hub
  air-compressor-services/   ├─ air-compressor-repair/
                             ├─ air-compressor-installation/
                             └─ air-compressor-maintenance/
  hydraulics-services/       ├─ hydraulics-repair/
                             └─ hydraulics-maintenance/
  mechanical-contracting/
  process-piping/
  preventive-maintenance/
/service-areas/            Service areas hub + 6 city pages
```

Every URL matches the paths on the current live site, so nothing breaks when
DNS is pointed here. `services/preventive-maintenance/` is the one addition:
it was marketed on the old homepage but had no page.

## Rebuilding

Requires Node 22.22+ and Python 3.9+ (for the checker).

```bash
npm install                      # once
npm run dev                      # live preview at http://localhost:4321
npm run build                    # build all 22 pages into dist/
npm run check                    # verify links, assets and metadata in dist/
```

| File | What it holds |
| --- | --- |
| `src/data/content.ts` | **All copy and data.** Services, service areas, nav, company details. Edit here. |
| `src/pages/*.astro` | Page-specific copy (hero text, page FAQs) and the order of sections. |
| `src/components/` | HTML components: nav, cards, bento, sections, photo. |
| `src/layouts/Base.astro` | Page shell: head metadata, structured data, nav and footer. |
| `_build/check.py` | Post-build validation of `dist/`. Exits non-zero on a broken link. |
| `_build/images.py` | Photo pipeline. Needs `_inbox/` and Pillow; only re-run when adding photos. |

### Changing text

Service and area copy lives in `src/data/content.ts`. To change a service
description, a service FAQ or the phone number, edit it there. Copy that only
appears on one page (the home hero, the contact FAQs) is in that page's file
under `src/pages/`. `dist/` is build output and is not committed.

**Two house rules for copy.** Both exist because they are the fingerprints of
machine-written text, and this site should not read that way.

1. **No em dashes.** Use a colon when a list follows, parentheses for a genuine
   aside, a full stop when the clause can stand alone, otherwise a comma.
2. **No "X, not Y" antithesis.** Say the thing directly instead of defining it
   against its opposite. "You get a technician, not a ticket number" becomes
   "a technician picks up the phone." The same applies to "not just X but Y",
   "instead of", and "rather than" when it is used for rhetorical contrast
   rather than a real comparison. "Measured in hours rather than days" is a
   genuine comparison and is fine; "diagnose the cause rather than repeating
   the repair" was rhetoric and got rewritten.

Verbatim customer reviews are exempt from both. They are quotes from named
people and are rendered as written.

### Logo

The logo kit lives in `brand/` (SVG masters for every lockup, plus
`COLORS.txt`). The site serves copies from `public/assets/img/logo/`:

| File | Used for |
| --- | --- |
| `bm-horizontal-full-color.svg` | Header logo |
| `bm-horizontal-reverse.svg` | Footer logo (dark background) |
| `bm-icon-white.svg` | Faint watermark on dark and red panels (one-colour, so it stays crisp when faded) |
| `bm-horizontal-full-color-1000w.png` | Logo in structured data for search |
| `favicon*`, `apple-touch-icon.png`, `android-chrome-*`, `maskable-icon-512x512.png` | Browser, phone and home-screen icons |

`public/favicon.ico` sits at the site root, and `src/pages/site.webmanifest.ts`
builds the web manifest. To change the logo, replace these files with new ones
of the same names. The social card (`og-image.jpg`) has the reverse logo baked
in; rebuild it with `python3 _build/images.py` after a logo change.

### Adding photos

1. Drop originals into `_inbox/photos/`.
2. Add an entry to the `PHOTOS` dict in `_build/images.py`.
3. `pip3 install Pillow && python3 _build/images.py` (writes to `public/assets/img/`)
4. Reference the new slug from `src/data/content.ts` or a page.

EXIF rotation is applied automatically. 25 of the original 49 photos needed it.

## Deployment

### Previews (Cloudflare Workers Builds)

Cloudflare builds every branch with `bash _build/pages.sh`, which installs
packages, builds the site with Astro for the domain root into `dist/`, runs
`check.py`, and serves it as configured in `wrangler.jsonc`. Each ticket branch gets a preview at
`cu-<task id>-bm-industrial-solutions.zach-s-portfolio.workers.dev`, linked
from the ticket. Everything served by Cloudflare carries
`X-Robots-Tag: noindex` until it serves the real domain.

### Site URL and path prefix

Two environment variables control the build (see `astro.config.mjs`):

| Variable | Default | Effect |
| --- | --- | --- |
| `SITE_URL` | `https://www.bmindustrialsolutionsllc.com` | Canonicals, sitemap, Open Graph and structured data |
| `BASE_PATH` | empty | Prefix for every internal link, for serving from a subpath |

The GitHub Pages project URL serves from a subpath:

```bash
SITE_URL=https://ridgelinedm.github.io BASE_PATH=/bm-industrial-solutions npm run build
python3 _build/check.py --base /bm-industrial-solutions
```

GitHub Pages would need an Actions workflow to build and publish `dist/`,
since the HTML is no longer committed. Cloudflare already builds it.

## Ticket automation

ClickUp tickets become PRs that Claude writes, and go live when you approve
them in ClickUp. The Cloudflare Worker in `~/Projects/ridgeline-ticket-worker`
turns ClickUp status changes and `@Claude` comments into GitHub
`repository_dispatch` events.

| ClickUp status | What happens |
| --- | --- |
| **submitted** | `ticket-spec.yml` (every new ticket lands here). Claude reads the ticket, its comments and the site, then either rewrites the description as a change spec (keeping the client's original request below it) and moves it to **ready to build**, asks the client a question in a comment and moves it to **waiting on client**, or, for anything outside the website, assigns the reviewer with a note and moves it to **in queue**. Set a ticket back to **submitted** after the client answers |
| **ready to build** | `ticket-to-pr.yml` reads the ticket, Claude edits the source on branch `CU-<task id>`, the workflow rebuilds, runs `check.py`, refuses changes to `.github/`, `_inbox/` or `CNAME`, opens a PR, comments the PR and preview links on the ticket, moves it to **internal review** and assigns the reviewer |
| **internal review** | You check the preview. Start a ClickUp comment with `@Claude <what to change>` to revise it (`ticket-revise.yml`); Claude comments back when the preview is updated. `@claude` on the PR also works (`claude-revise.yml`) |
| **deploy** | `ticket-deploy.yml` squash-merges the PR, which publishes it, and sets the ticket to **complete**. If it cannot, it comments why and moves the ticket back to internal review |

Merging the PR on GitHub yourself also works: `ticket-merged.yml` then closes
the ticket. Both ticket workflows can be run by hand from the Actions tab with
a task ID. Claude's standing instructions for the repo are in `CLAUDE.md`.

| Setting | Kind | Value |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` | secret | Claude credentials (one of the two) |
| `CLICKUP_API_TOKEN` | secret | ClickUp personal token (`pk_...`) |
| `CLICKUP_REVIEWER_ID` | variable | ClickUp user assigned for review (`174105881`, Zach) |
| `PREVIEW_URL_TEMPLATE` | variable | Preview link, `{branch}` replaced by the branch alias |
| `CLICKUP_REVIEW_STATUS` | variable | Defaults to `internal review` |
| `CLICKUP_DONE_STATUS` | variable | Defaults to `complete` |
| `CLICKUP_BUILD_STATUS` / `CLICKUP_QUESTION_STATUS` / `CLICKUP_HUMAN_STATUS` | variable | Spec outcomes; default `ready to build`, `waiting on client`, `in queue` |

The repo allows Actions to open PRs, and `main` requires a PR (no approvals).

## Reviews

Reviews are imported from a Google Business Profile export. They are never
hand-written: if `_build/reviews.json` is missing or empty, the reviews section
does not render at all.

```bash
# 1. Drop the export into _inbox/reviews/ (or leave it loose in _inbox/
#    as long as the filename starts with "review"). .json or .csv both work.
python3 _build/reviews.py     # 2. parse it into src/data/reviews.json
npm run build                 # 3. rebuild the pages
```

`_build/reviews.py` understands the Business Profile API shape (nested
`reviewer.displayName`, word ratings like `"FIVE"`, ISO `createTime`), a flat
JSON array, or a CSV with any sensible header naming. It de-duplicates across
files, drops star-only ratings that have no comment to display, and sorts
longest-first so the masonry fills evenly.

Two counts come out of it: `count` is reviews with written text (what gets
rendered as cards) and `total` is every rating on the profile (what the
headline score is calculated from), so the "N reviews" figure matches Google
rather than the number of cards on screen.

The raw exports stay in `_inbox/`, which is git-ignored — they carry your
account and location IDs. Only the parsed `reviews.json` is committed.

Review text is rendered verbatim. The importer strips two things that are
decoration rather than content: a leading row of star emoji some people type,
and a trailing rule like `————`. Punctuation *inside* a review is left exactly
as written, because these are attributed quotes from named people.

Set `ABBREVIATE_SURNAMES = True` at the top of `_build/reviews.py` to render
"Jane D." instead of full names.

**No `aggregateRating` schema.** The star rating is displayed but deliberately
not marked up in structured data. Google disallows self-serving review markup
on `LocalBusiness`, and adding it risks a manual action against the whole
site's rich results. The reviews still work as social proof for humans.

## Design notes

Brand colours were sampled from the logo artwork: red `#CE171E`, ink `#231F20`,
grey `#686868`. Type is DM Sans throughout. Archivo was the original headline
face; to bring it back, follow the note above `FONT_CSS` in
`src/layouts/Base.astro`. Icons are [Phosphor](https://phosphoricons.com) (bold
weight, MIT), generated into `src/components/icons.ts`.

The layout follows the reference site's language rather than just its spacing:

- **Bento grid** (`.bento`). The service lines render as an asymmetric grid of
  solid colour-blocked panels at mixed widths, with photography bleeding to the
  card edge. The reference uses lavender/yellow/pink; we use the only palette
  the brand owns: ink, red, and two industrial neutrals (`#efece6` bone,
  `#e4e8ea` mist), plus a full-bleed photo surface. Layout is configured in
  `BENTO_LAYOUT` in `src/components/sections/ServicesShowcase.astro`.
- **Ring button** (`.btn--ring`). A filled pill inside an offset outline with a
  gap of background colour between, driven by `--ring-gap` and `--ring-line`.
- **Split section heads.** Any left-aligned heading with supporting copy
  automatically renders as two columns, heading left and lead right.
- **Accented headline words.** `<em>` inside a heading prints in brand red, and
  inverts on red and ink grounds so it never disappears into its background.
- **Bare icon grids** (`.featurelist`) and muted wordmark walls instead of the
  boxed-icon card and chip-row patterns they replaced.
- **Headings stand alone.** No label above a heading unless it says something
  the heading does not (the city distance, "The owner", the 404 code). Footer
  headings are sentence case at a readable size.
- **Reading tone.** Running text uses `--text-soft` (about 9:1). Keep
  `--text-muted` for secondary notes only; every text colour clears 4.5:1.
- **Numbered steps** (`.steps`) and **FAQ beside its heading**
  (`FaqSection`) replace an icon-card row and a centred accordion.
- **One grey family.** The `--grey-*` ramp is warm, tinted toward the brand
  ink. Surfaces are defined by fill, without 1px outlines.

Accent colours are deliberately limited to the brand palette. If you add a new
surface, check the `em` accent still has contrast against it.

Accessibility and performance basics are in place: one `<h1>` per page, alt text
on every image, visible focus rings, `prefers-reduced-motion` honoured, skip
link, responsive `<picture>` sources at four widths with JPEG fallbacks, and no
external requests other than Google Fonts.
